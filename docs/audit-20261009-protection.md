# Bitget TP/SL audit — protection slice (2026-10-09)

Scope: native protection payload/readback, async venue price admission, capability policy/storage, GET-only protection recovery, fallback REST/stream close paths, and watchdog. Implementation is local only. No production orders, cancellations, configuration changes, builds, tests, or formatters were executed by this slice.

## Provider contract evidence

The following Bitget Classic V2 references were read in full through the `www.bitget.work` host. Each page declares the linked `www.bitget.com` URL as canonical; the canonical host's certificate prevented direct retrieval in this workstation environment.

- [Place position TP/SL](https://www.bitget.com/legacy-docs/classic/contract/plan/Place-Pos-Tpsl-Order): `/api/v2/mix/order/place-pos-tpsl`; omitted leg size creates `pos_loss`/`pos_profit`; explicit size creates `loss_plan`/`profit_plan`. Execution price omitted or `0` means market, positive means limit. `holdSide` is `buy`/`sell` for one-way and `long`/`short` for hedge mode. Both client OIDs and array placement responses are documented.
- [Pending trigger orders](https://www.bitget.com/legacy-docs/classic/contract/plan/get-orders-plan-pending): `data.entrustedList`; `planType=profit_loss` queries all five protection plan types. `posSide` expresses position direction (`long`, `short`, `net`), while `side` expresses order direction. Example status is `not_trigger`, whereas the field description says current orders have `live`; verification now accepts both documented forms. Page maximum is 100.
- [Single position](https://www.bitget.com/legacy-docs/classic/contract/position/get-single-position): `total` is available plus locked base quantity, `holdSide` is long/short, `posMode` reports one-way/hedge, `stopLossId`/`takeProfitId` and prices are exposed, and `cTime` is creation time.
- [Place order](https://www.bitget.com/legacy-docs/classic/contract/trade/Place-Order): `side` is buy/sell execution direction in one-way; `tradeSide` is ignored in that mode, and `reduceOnly` applies only to one-way. Hedge close semantics are different. A reduce-only acknowledgement can legitimately omit `orderId`; acknowledgement is not fill proof.
- [Historical plans](https://www.bitget.com/legacy-docs/classic/contract/plan/orders-plan-history): `executed` means the plan triggered, not that the resulting exit completely filled; `executeOrderId` identifies the resulting order. `baseVolume` describes execution quantity. `fail_execute`/`cancelled` are not protection.
- [Ticker](https://www.bitget.com/legacy-docs/classic/contract/market/Get-Ticker): `lastPr` and `markPrice` are distinct documented fields.

## End-to-end trace and intentional boundaries

1. Entry fill reconciliation supplies confirmed filled base quantity, not requested quantity, to native placement. Entry/precision/partial-cancellation changes belong to the entry slice.
2. Native payload sets mark triggers and market exits, with stable entry-derived leg client OIDs. Size omission is full-position semantics; explicit sizes are per-order semantics. The provider response is only acknowledgement: fresh position and exact pending plans are required before upgrading protection.
3. A plan becoming `executed` is no longer active protection and is not itself a canonical close fill. Real resulting order/fill IDs, quantities, average price and fees are required for accounting. Fallback close persistence already reconciles canonical fills and retains `closing` for unknown/partial results; this audit preserved its no-second-POST invariant.
4. Fallback ownership remains strict: environment, entry key, provider position epoch, side and exact quantity must match durable entry proof. Legacy rows are intentionally not mutation-eligible. This audit did not loosen ownership to close aggregate or replacement exposure.
5. GET-only restart recovery requires canonical entry fill IDs and compares a provider-backed native expectation. It never places protection, registers fallback or closes exposure. Parent owns recovery incident/deployment and changes to `service.py`/dispatcher.
6. Capability storage keys include environment. Fresh stream events do not automatically allow fallback; native verification and fallback permission are independent fields. Repository update behavior and historic native-verification retention were reviewed without changing policy, risk settings or schema.

## Remaining risks / decisions needed

- **Multiple TP targets are not partitions today.** `async_execution.protect_filled_position` and GET-only recovery select `take_profits[0]`; both native position TP and fallback nearest-TP close cover the full quantity. Local operations docs describe source TP1 closing 50% then moving SL to entry, which is a separate source-management policy. No general TP allocation weights were found in the signal/domain/config; silently inventing equal weights would change trading strategy. The parent was notified. Full-size first-target behavior is not represented as a completed multi-target feature.
- **Residual exposure after partial exits needs canonical lifecycle ownership.** Native position SL is deliberately independent of sized TP legs. Fallback ownership rejects a provider quantity different from its registered entry quantity; loosening that to a smaller arbitrary total would also authorize unrelated manual changes. A source partial exit or a partially filled fallback close needs a durable, matched fill-ledger residual before any new close identity can be considered safe. Existing `closing` recovery reads evidence and does not resend.
- **Pending-plan pagination.** Provider limits pending queries to 100 rows. A first-page-only read may degrade protection when its IDs are beyond that page. It must never convert truncated or unavailable inventory into proof. Targeted OID/order-ID reads or complete pagination belong at the HTTP boundary.
- **Provider position-plan size shape needs a GET-only canary.** Documentation distinguishes omitted-size position plans, but does not demonstrate a position TP/SL pending row with its actual `size` value. Existing strict zero/empty size expectation is retained; a contradictory positive size is not optimistically treated as full-position coverage.
- **Executed native plan to fill linkage.** Historical plans expose `executeOrderId`; real close fills may have a different order ID from the plan. Recovery/accounting must correlate those identities, not treat placement ID or missing open position as a filled close.
- **Native capability observation is historical.** `can_admit_symbol` accepts `VERIFIED` without an age TTL. New fills still need exact placement/readback, but an old capability is not proof an existing position is protected now.
- **Trigger vs current mark vs actual fill.** Signal trigger geometry and price precision must be validated at the entry boundary; the fallback cannot swap mark for fill/last trade to make an invalid signal pass. Native market execution does not promise execution at the trigger price.
- **Hedge mode is intentionally unsupported for this bot lane.** Provider supports it, but production preflight, readback and fallback now explicitly require isolated one-way. No account mode/risk changes were made.

## Admission precision follow-on

The admission boundary now applies the existing half-up `round_price_to_tick` to the canonical SL and every TP before live sizing/liquidation checks. Rounded stops and targets must remain on the correct side of both canonical entry and current admission price, with at least one tick separation; targets collapsing to the same tick are rejected before reserving margin.

The source signal remains unchanged. Immutable admission carries `planned_stop_loss` and `planned_take_profits`; the entry intent claim persists these separately in `live_order_intents` (NUMERIC SL and JSONB decimal-string TP array). Native protection and GET-only recovery read that same durable execution plan, never recompute from the source or a later preflight. Historical intents without a validated plan remain unresolved with `recovery-validated-plan-missing`; no migration invents historical prices or changes fills, fees, PnL or provider identifiers.

Precision regression coverage adds both-side half-up boundaries, rounding that collapses geometry or TP spacing, a raw-stop-pass/rounded-stop-fail liquidation-buffer boundary, exact persistence decoding, and restart recovery retaining the winning plan despite changed source/admission values. No tests, builds, formatters, provider POSTs or remote mutations were run by this follow-on. The integration owner should run the admission contract, service admission wiring, adapter, intent admission persistence and entry lifecycle recovery unit suites plus existing PostgreSQL service/recovery suites after migration integration.
