# Bot Management Console: phase 0 capability and safety specification

## Status, authority, and evidence boundary

**Phase 0 source assessment is complete for the kickoff scope; this is a specification, not a console implementation or live acceptance report.** The baseline inspected is `origin/main` at `ea0114e`, in the isolated console working clone. No source, provider account, production configuration, running service, safety latch, or risk limit was changed by this assessment. No provider/production probes, builds, tests, linters, or formatters were run by the author of this document. Source inspection establishes an implementation boundary, not that its deployed dependencies, credentials, migrations, gates, or readbacks currently work.

Read this together with the master plan/progress tracker and phase 1 UI/API contracts. All console `/api/v1` routes, durable console jobs/approvals, sessions, SSE, and React screens described by those contracts remain **proposed**. Existing web application routes are only `GET /health` and `GET /health/telemetry` [E01]. The separate recovery application is not that web application's command API [E11]. Evidence below identifies inspected source boundaries rather than deployed capability.

Authoritative constraints are [AGENTS.md](../AGENTS.md), [TRADING-RULES.md](TRADING-RULES.md), and [PRODUCTION-LIVE-POLICY.md](PRODUCTION-LIVE-POLICY.md). Production remains **LIVE/LIVE/1**; execution enabled is necessary but never sufficient permission to trade. An implementation plan does not authorize deployment, trades, Telegram sends, consumer shutdown, latch release, baseline application, credential rotation, or risk changes.

### Classification used below

- **R — existing read boundary:** actual read adapter/query exists. It still needs an authenticated console DTO, provenance/freshness/error handling, and wiring; this is not an existing web feature.
- **S — existing bounded mutation/reconciliation boundary:** durable provider ownership/intent and readback exist for the specifically named workflow. Console authorization, approval, job, and caller integration are still prerequisites. S is not permission to execute now.
- **L — legacy/direct mutation boundary:** callable provider/DB operation exists, but it does not meet the complete reusable console mutation contract. Keep the proposed console action gated until the stated gap is closed; do not present it as a safe adapter.
- **G — grammar only / explicitly refused:** parser/protocol accepts the request but the production adapter does not implement it, or the requested target/venue is rejected. A confirmation token does not change this.
- **M — missing console/domain action:** no integrated boundary for that operator behavior in the inspected production graph. A shell script, environment variable, or SQL table is not itself an authenticated command.

The phase 1 capability response uses `available | gated | unsupported | read_only`. These assessment classifications are more detailed implementation evidence, not a competing API enumeration: R maps to `read_only` only after web wiring; S and L map to `gated` until their required console integration exists; G/M map to `unsupported` unless a newly implemented adapter is deliberately shipped. At this baseline none of these actions is an implemented `/api/v1` capability.

### Manual entry must join admission, not sidestep it

**P-MANUAL-ENTRY** is a real implementation prerequisite, not “connect form to `open_position`.” The existing production entry path has constraints absent from the refused operator adapter:

1. Fresh authenticated futures account/position evidence, metadata legality, Decimal financial values and immutable plan/protection prices; full symbol/side/account identity.
2. Existing pinned LIVE risk policy: fixed 1 USDT per-trade margin cap and 20x ceiling, configured permitted leverage floor, positive position limit, no floor-escape margin; normalized stop/liquidation and quantity/notional checks. Source preflight enforces these in E07; browser quantity/margin/leverage fields cannot bypass them.
3. Atomic margin admission/reservation and account-baseline exclusion; concurrent web/Telegram/source work must compete for the same commitments, not each see the same available balance as independently spendable.
4. Explicit manual provenance rather than a fabricated Telegram source message. Decide and implement legitimate manual admission evidence while preserving source revision/freshness fences for real source entries. Manual requests cannot impersonate a fresh source to sneak through eligibility SQL.
5. Durable stable root/child OIDs, planned quantities/prices/protection and claim before POST; working LIMIT/partial ownership must survive restart. Exact 25/75 applies to the owner-selected recent-source route, not arbitrarily to every manual trade.
6. Global/venue/protection-stream latches and final entry fence after awaited provider preparation; unknown results reconcile GET-only. Preserve protected actual aggregate filled quantity when a LIMIT remainder later fills.
7. A shared typed command implementation invoked by both web and Telegram; remove obsolete direct parser-to-gateway behavior at cutover. Never ship a web-only fast path while legacy Telegram open/cancel/protection retains different safety semantics.

Existing verified-close binding additionally joins a `canonical_signal` dispatch, consumed reservation and owned entry; refuses unresolved waiting LIMIT legs, ambiguous owners and a close larger than the proved residual. Reconciliation requires exact authenticated non-status-derived fill identities/economics and fresh both-side flat evidence before release [E09]. Manual-entry implementation must extend legitimate manual ownership through this close/reservation lifecycle, not merely implement opening while leaving subsequent closes unbound.

Until this is implemented end to end, manual MARKET/LIMIT actions remain unsupported even if a UI renders their forms or accepts a preview.

## 6. Ownership, concurrency, confirmations, and truthful outputs

### Authority and ownership are different

Provider position/order existence proves account state, not bot ownership. Durable ENTRY roots/children, provider client/order/fill IDs, prebound exits, source revisions and audited account baselines establish the narrower ownership needed by existing lifecycle boundaries [E08/E09/E13]. Source-management cancellation may select only exact durable remaining ENTRY legs, never native SL/TP, reduce-only close, protective plan, baseline/manual/unrelated orders. Selecting a symbol is not sufficient authority to cancel everything under it.

The source CLOSE/TP1 contract explicitly acts on a freshly read symbol position after cancellation; do not silently claim that any aggregated provider position is a separately partitionable “bot position.” Generic operator close/all currently reads account provider positions. New console previews must disclose bot/manual/baseline/unknown scope and require corresponding authority; they must preserve the owner-selected source behavior rather than rewrite it without approval.

The shared command layer owns authorization, normalized intent, stable idempotency identity, actor/approval and durable job dispatch. Existing specialized execution/store boundaries own venue admission, provider claims/POST/readback, exact quantity and lifecycle state. Host operations remain in a separate privileged, typed allowlisted executor; the web process never owns Docker socket access, unrestricted shell, raw SQL repair, or exchange credentials returned to the browser.

### Current confirmations are not durable approvals

`OperatorCommandService` holds one `_pending` confirmation and token in memory; issuing another challenge replaces it; restart loses it; expiry is 300 seconds. The action kind/fingerprint binds the repeated command, but does not bind a durable account/target preview snapshot or a versioned risk policy. Telegram receipt storage durably prevents reexecuting the **same Telegram update ID**, not repeating the economic action in a new update or through web [E03/E17]. Operator closes choose a fresh OID per call [E04].

Therefore a shared durable approval/job cutover must cover both web and Telegram, not retain these tokens as a second mutation authority. Store exact normalized parameters, target identities, expected state/version, policy and preview digest, requester/approver, approval expiry and consumed/revoked state. A challenged command is not an intent that already reached the venue. On timeout, crash, repeated job or existing provider claim, recover the same identity via readback; do not issue a new POST or a new “retry trade” ID.

### Failure and evidence contract

- **Preview/auth/gate/admission refusal:** no provider mutation claimed; return exact safe reason code and required prerequisite. Do not display “success” because input parsed, a token was consumed, or a queue insert succeeded.
- **Durably queued/approved/claimed:** transport/job states only. Preserve claim time, target and correlation IDs; show provider state separately.
- **Provider acknowledgment:** submitted/accepted, not filled, flat, protected or reconciled. Ordinary cancellation legacy text/count is weaker still and must not be upgraded to terminal evidence.
- **Unknown acknowledgment, malformed response, timeout or lost claim:** retain durable intent and reconciliation-pending/unknown. UI reload, SSE reconnect, worker restart, browser double-click and second channel must not trigger a fresh POST.
- **Partial bulk completion:** report each target independently, including attempted/submitted/unknown/refused/not-open. Never compress “some” into “all.”
- **Position readback:** can prove current position reduction/flatness under the specific workflow; cannot by itself prove provider fill economics or which prior action caused flatness. Verified-close storage owns that stronger claim.
- **Protection:** reported price/registration, strict owned plan/coverage readback, and fresh runtime enforcement are separate facts. Native/fallback absent, unavailable and stale remain distinct.
- **Source terminal outcomes:** retain `cancelled-flat`, `entries-cancelled`, `reconciled`, `reconciliation-pending`, and `failed`. The first two must never manufacture close/TP fills or stop changes [E10/TRADING-RULES].
- **Deployment/backup/restore:** command acceptance, exit outcome, observed target state and post-operation validation are separate evidence. No implied rollback or live enablement from a green service indicator.
- **Notification:** deduplicated outbox row and Bot API delivery evidence are transport facts only. The auto-recovery script's direct Telegram alert is not the durable outbox despite its helper docstring [E11/E18].
