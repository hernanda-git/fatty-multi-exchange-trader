# Bitget entry execution and sizing audit — 2026-10-09

Scope: local clone of production source commit `1e4720d`; REST signing/client, contract metadata, sizing, one-way entry/close payloads, async and compatibility execution readback, and dispatch/routing admission. No orders, signal replay, remote mutations, secrets, or risk-setting changes. Tests/build/lint/formatters were not run by this worker.

## Confirmed defects repaired

1. **Incorrect price tick.** `metadata_from_contract` previously treated `10^-pricePlace` as the whole tick and ignored `priceEndStep`. A contract with place `1` and end step `5` requires multiples of `0.5`, not `0.1`. Corrected the multiplication and migrated incorrect fixtures that used an already-scaled decimal as `priceEndStep`. Regression rejects `50000.2` and accepts `50000.5`.
2. **Order quantity limits had the wrong units and order type.** `maxPositionNum` was used as a base-coin order quantity despite being a maximum position COUNT. `maxOrderQty` (limit order maximum) also won over `maxMarketOrderQty`, even though production submits market entries. Metadata now preserves distinct optional limit/market maxima and never converts a position count into quantity. Removed the undocumented `maxTradeNum` compatibility fallback and migrated fixtures to V2 fields. Local order validation can explicitly select the order type. Production live sizing floors to the market quantity ceiling before reserving margin; it does not split an oversized order or modify risk settings.
3. **Step-flooring misreported committed margin.** With no configured per-trade margin cap, `_enforce_margin_cap` returned the original allocation even when quantity flooring or an exchange ceiling reduced the notional. That margin was persisted/reserved and used by liquidation and post-fill comparison. Margin is now always derived from final quantity × entry / leverage. Regression: entry `101`, allocation `200`, leverage `20`, step `.001` gives qty `39.603`, notional `3999.903`, margin `199.99515`, not the unspent allocation `200`.
4. **V2 order state and canceled partial fills were mishandled.** Official order detail uses `state`, while `classify_live_order` read only `status`. It also classified cancellation before checking fills, and ignored detail-only partial execution. A canceled remainder can leave a real open position; treating it as rejected can skip protection and release margin. The shared classifier now reads V2 `state`, includes documented cumulative `baseVolume`, and reports partial/full execution before cancellation/rejection. Sync readback retains detail quantity/average when the fill page is incomplete. Async readback also uses larger cumulative detail quantity rather than protecting only a subset from a recent fill page.
5. **Malformed fill rows fabricated full executions.** Async readback promoted an accepted order with any matching fill row to FILLED and assigned the entire requested quantity, even if that row contained no usable quantity. Removed this branch. A malformed row no longer establishes execution or invents a quantity.
6. **Provider timeout/unknown errors became definitive rejections.** HTTP 200/400 error envelopes with `40010` (request timed out), `40725` (service returns an error), or `45001` (unknown error) were ordinary `BitgetApiError`s. The dispatcher could reject/release an intent despite an unknown server-side mutation result. These mutation codes now raise `BitgetUnknownResultError`, preserve provider code/status, and enter the existing GET-only reconciliation path; POSTs are never retried. GET error behavior is unchanged. Entry/close success envelopes with invalid non-object data also remain UNKNOWN rather than becoming definitive provider rejections.
7. **Compatibility replay mutated setup first.** `enter_live_position` performed new-entry preflight and margin/leverage setup before checking an existing durable client OID. Existing intents now reconcile before new-entry setup; they do not repost or reset leverage. Existing conditional protection behavior is retained.

Decimal normalization used by metadata and shared order readback now rejects non-finite values instead of letting NaN comparisons break the workflow.

## Audited contracts and preserved behavior

- Signing concatenates millisecond timestamp, uppercase method, exact request path, the exact encoded query when present, and compact JSON body, then HMAC-SHA256 and Base64. The actual bytes sent use the same query/body as signing. No evidence of a signing serialization defect was found.
- Production explicitly admits isolated one-way accounts. In that mode BUY/SELL are execution directions, `tradeSide` is ignored, and `reduceOnly=YES` is the correct close constraint. Hedge mode requires different close semantics and is intentionally refused; it is not silently converted. Limit entries correctly use `force=gtc`; market entries omit price. A reduce-only success response can legitimately omit orderId, so missing orderId alone is not rejected.
- Durable intent precedes entry POST. Transport failures, 5xx responses, malformed mutation envelopes, and the repaired provider timeout codes flow through unknown-result handling. There is no blind POST retry.
- Production preflight uses provider current price for sizing, not the stale signal price. Leverage setup is followed by account-mode/leverage readback. Existing admission guards, stop-before-liquidation guard, durable margin evidence, source-freshness/winning-claim boundary, and kill-switch checks remain in place.

## Remaining risks and capability boundaries

- **Native trigger entries are not implemented in the production call path.** `AsyncBitgetExecution._submit_entry` always calls market `place_entry_order`; there is no `place-plan-order` method/caller or durable trigger-price/type/order-type contract. `route_entry` is a pure LIMIT/MARKET/split decision function, not a native trigger implementation. Production assembly does not supply `entry_routing`; enabling it against the existing execution adapter fails closed as `entry-routing-unsupported`. It is unsafe to infer a new wait/trigger policy or implement an untracked plan POST merely because Bitget provides one. Native entry-plan requirements (trigger direction, mark vs last price, expiration/cancellation, admission reservation lifetime, durable normal-plan IDs and readback) require an explicit product policy. This is distinct from a bot-side signal-trigger/watch command.
- `route_entry`'s 25/75 split does not quantize child quantities or ensure each child meets min notional. There is currently no production routed-order consumer; any future activation must round/safely allocate both legs against fresh contract metadata and carry the same immutable admission evidence rather than only a Decimal quantity.
- SL/TP signal prices are forwarded to native placement without a contract-tick rounding contract in the entry intent. Off-tick signal protection can still be rejected by the provider; do not disable containment. Protection worker owns its contract/verifier slice.
- Only the current fill page is fetched. Cumulative detail quantity now preserves the correct exposure when that page is incomplete, but historical fill identities/fees still require paginated provider-fill reconciliation for exact accounting. No synthetic fill IDs/fees were added.
- The liquidation module is a conservative estimate, not the exchange's complete engine formula (tier maintenance deductions, funding, fee changes, tier leverage and market slippage can matter). A provider position's actual liquidation price remains authoritative. Contract maximum leverage alone does not represent every size-tier leverage constraint.
- Post-fill actual margin may differ from planned margin because of execution-price slippage, fees, and provider precision. The existing absolute `0.01` mismatch policy is unchanged; a legitimate larger slippage difference can still degrade entry admission. Changing tolerance/risk policy requires an explicit decision, not an audit-time bypass.
- Provider-account migration to UTA, API permissions/region/IP restrictions, symbol API status, venue clock/latency, rate budget, actual historical fills and account mode cannot be inferred from offline fixtures. Those require read-only provider evidence. No claim is made that historical production failures were all caused by these local defects.

## Parent verification scenarios

Run once after integration: `tests/unit/test_bitget_client.py`, `test_bitget_validation.py`, `test_live_sizing.py`, `test_bitget_async_venue.py`, `test_bitget_async_execution.py`, `test_bitget_live_orders.py`, plus dispatcher/admission/reservation/reconciliation/protection suites.

1. Tick mantissa 5/precision 1 rejects non-multiples; ordinary mantissa 1 fixtures remain valid.
2. Limit max 1000 / market max 500: market size 501 rejects, limit size 501 validates. Missing quantity maxima with maxPositionNum 150 does not impose a fake 150-coin cap. Live planning floors a non-step-aligned market ceiling and reserves actual margin only.
3. Uncapped floor-rounded plans satisfy `margin = notional / leverage` and preserve all configured margin/position/liquidation guards.
4. Exact V2 `{state, size, baseVolume, priceAvg}` readback handles live, partial, filled, canceled-unfilled, and canceled-partial. Canceled partial exposure must reach protection and keep its reservation; a cumulative detail larger than the recent fill page protects the cumulative amount.
5. A matching malformed fill without size never fabricates a full fill. Existing full-fill fixtures without any authoritative quantity remain UNKNOWN.
6. Each `40010`, `40725`, `45001` at HTTP 200 and 400 produces UNKNOWN/GET reconciliation and exactly one POST; invalid success data does the same. Definite validation/auth failures remain ordinary provider failures.
7. Existing durable sync intent can reconcile when new-entry admission/setup is unavailable, without entry POST or leverage/margin setup.
